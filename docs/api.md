# API — DummyJSON

База: `https://dummyjson.com`. Без ключа, без ліміту запитів. Всього ~194 товари, 24 категорії.
Документація: https://dummyjson.com/docs/products

## Що використовуємо

| Задача | Запит | Що повертає |
|---|---|---|
| Список + пагінація | `/products?limit=20&skip=40` | `{ products, total, skip, limit }` |
| Сортування | `/products?sortBy=price&order=asc` | те саме |
| Пошук | `/products/search?q=phone` | те саме |
| Товари категорії | `/products/category/smartphones` | те саме |
| Список категорій | `/products/category-list` | масив слагів: `["beauty", ...]` |
| Один товар | `/products/1` | обʼєкт товару |
| Економія трафіку | `?select=id,title,price,thumbnail` | тільки вказані поля |
| Імітація повільної мережі | `?delay=1500` | те саме, але через 1.5 с |

`total` — це кількість товарів, що відповідають запиту (не завжди 194), і саме з нього
рахується кількість сторінок: `Math.ceil(total / limit)`.

`?delay=` — робочий інструмент, а не забавка: без нього loading-стани й race conditions
на локальній машині майже не спостерігаються.

## Поля товару, які нам потрібні

`id`, `title`, `description`, `category`, `price`, `discountPercentage`, `rating`, `stock`,
`brand`, `thumbnail`, `images`.

Решту полів (`dimensions`, `meta`, `reviews`, `sku`, `weight`…) у тип **не додаємо**: тип описує
контракт, який ми використовуємо, а не все, що прилетіло. Зайві поля — це зайві причини
правити тип.

`discountPercentage` — це **процент**, а не кінцева ціна. Ціну зі знижкою рахуємо самі
(`lib/`), і бейдж `-15%` малюємо з того самого поля.

`stock` — джерело правил кошика (не даємо додати більше, ніж є) і бейджів наявності.

## Обмеження, які впливають на архітектуру

**1. Пошук і категорія не комбінуються.** Немає `/products/search?q=phone&category=smartphones`.
Це два різні endpoint-и, і перетин доведеться або будувати на клієнті, або заборонити в UI.

**2. Фільтра по ціні немає взагалі.** Тільки клієнтська фільтрація вже завантажених товарів,
що конфліктує з серверною пагінацією → ADR-007.

**3. Мутації фейкові.** `POST /products/add`, `PUT`, `DELETE` повертають правильну відповідь,
але нічого не змінюють на сервері. Тому кошик — виключно клієнтський стан; endpoint `/carts`
не використовуємо.

**4. Немає лічильників по категоріях.** «Laptops (24)» біля фільтра зробити не вийде без
24 окремих запитів. Свідомо не робимо.

**5. `brand` є не в усіх товарів.** У частині категорій (наприклад, `groceries`) поле відсутнє —
тип мусить це відображати, інакше TypeScript дозволить звертатись до `product.brand` як до
гарантованого рядка й ми отримаємо `undefined` у розмітці.

## Обробка помилок

`fetch` не кидає виняток на 404 і 500 — перевіряємо `response.ok` вручну.
Технічні помилки (мережа, 5xx) і «не знайдено» (404 на `/products/9999`) — різні стани в UI:
перше це «спробуйте ще», друге це «такого товару немає».
