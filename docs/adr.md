# Архітектурні рішення (ADR)

Кожен запис: **рішення → контекст → чому так → альтернативи → наслідки**.
Записуємо в момент прийняття, не post factum. Рішення не переписуємо — якщо змінили думку,
додаємо новий ADR зі статусом «замінює ADR-N».

---

## ADR-001 — Zustand як сховище стану

**Статус:** прийнято

**Контекст.** У проєкті три групи стану: вміст кошика, параметри фільтрації, стан інтерфейсу
(відкритий drawer). Кошик читають і змінюють мінімум 4 віддалені точки: картка в каталозі,
сторінка товару, drawer, сторінка `/cart`. Через props це не передати.

**Чому Zustand.**
- Компонент підписується на **конкретне поле** через селектор і ре-рендериться тільки при його зміні.
- Стор — це звичайний обʼєкт поза React: доступний з утиліт і тестів через `getState()`, без рендеру.
- Немає Provider-обгортки, немає boilerplate екшенів/редюсерів.
- Логіка кошика тестується як звичайна функція.

**Альтернативи.**
- *Context API* (використаний у попередньому проєкті) — зміна значення контексту ре-рендерить
  **усіх** споживачів. При 20 картках у сітці зміна кількості одного товару перемалює всі 20.
- *Redux Toolkit* — вирішує ту саму задачу, але з більшою церемонією; свідомо відкладено на
  наступний проєкт, щоб порівняти підходи на власному досвіді.
- *URL + useState* — не покриває кошик.

**Наслідки.** Треба дисциплінувано писати селектори (`useCartStore(s => s.items)`), а не тягнути
весь стор — інакше втрачаємо головну перевагу. Ре-рендери перевіряємо React DevTools Profiler.

## ADR-002 — DummyJSON як джерело даних

**Статус:** прийнято

**Контекст.** Потрібен безкоштовний REST API з достатньою кількістю товарів, у якого є пагінація,
сортування й категорії — інакше ці теми нічим відпрацювати.

**Чому DummyJSON.** ~194 товари, 24 категорії, `limit`/`skip` + `total` у відповіді, `sortBy`/`order`,
пошук, поле `stock` (для правил кошика) і `discountPercentage` (для бейджів). Без ключа й реєстрації.
Є параметр `?delay=`, яким можна штучно вповільнити відповідь і подивитись на loading-стани.

**Альтернативи.** FakeStoreAPI — 20 товарів, немає нормальної пагінації. Локальний `json-server` —
дає повний контроль, але прибирає реальну мережу разом з таймаутами й race conditions, які нам
якраз потрібні для навчання.

**Наслідки.** Два обмеження API впливають на архітектуру фільтрів — див. ADR-007 і `docs/api.md`.

## ADR-003 — React Router 8, стан фільтрів в URL

**Статус:** прийнято

**Контекст.** Три сторінки: каталог, товар, кошик. Плюс питання, де жити параметрам фільтрації.

**Рішення.** Маршрути `/catalog`, `/product/:id`, `/cart`. Фільтри, сортування й номер сторінки —
**в query-параметрах URL** (`/catalog?q=phone&category=smartphones&sort=price-asc&page=2`),
а не в Zustand.

**Чому.** URL — це вже сховище стану, яке дає безкоштовно: кнопку «назад», F5 без втрати вибірки,
можливість скинути посилання. Дублювати те саме в стор — означає мати два джерела істини й
синхронізувати їх вручну.

**Наслідки.** Джерело істини для фільтрів — `useSearchParams`. Zustand відповідає за кошик і UI,
але **не** за фільтри. Читання/запис query-параметрів інкапсулюємо в один хук, щоб компоненти
не знали назв параметрів.

**Примітка по версії.** У React Router 8 пакета `react-router-dom` більше немає — імпорти з
`react-router`. Мінімум Node 22.22.

## ADR-004 — Окремі стори: `cart` і `ui`

**Статус:** прийнято

**Рішення.** `cartStore` (позиції, кількості, дії над ними) і `uiStore` (`isCartOpen`) — різні стори.

**Чому.** Один стор = одна відповідальність. Стан «drawer відкритий» — це властивість інтерфейсу,
а не даних кошика: він не зберігається між сесіями, не бере участі в підрахунку суми і змінюється
у 10 разів частіше. Змішування зробило б `persist` (ADR-005) складнішим, бо частину полів
довелося б виключати з серіалізації.

## ADR-005 — Збереження кошика через `persist` middleware

**Статус:** прийнято

**Рішення.** Кошик зберігається в localStorage через вбудовану мідлвару Zustand `persist`,
а не через власний хук `useLocalStorage`.

**Чому.** Збереження — це наскрізна поведінка, а не частина логіки кошика. Мідлвара додає
серіалізацію одним рядком і дає `version` + `migrate`: коли форма `CartItem` зміниться,
у користувача в сторажі вже лежать дані старого формату, і без міграції додаток впаде.

**Наслідки.** Зберігаємо тільки `items` (`partialize`). Ціни й наявність **не** довіряємо
сторажу — вони могли змінитися; при відкритті кошика показуємо збережені дані, але це компроміс
навчального проєкту, і він тут задокументований свідомо.

## ADR-006 — Без dark mode

**Статус:** прийнято

**Чому.** Подвоює кількість станів для перевірки на кожному екрані, а тема проєкту — стан, не CSS.
Токени вибрані так, що додати тему = один блок перевизначень.

## ADR-007 — Фільтрація по ціні: сервер чи клієнт

**Статус:** ВІДКРИТО — вирішуємо на Кроці 4

**Контекст.** DummyJSON не має фільтра по ціні, і не дає комбінувати пошук з категорією
(див. `docs/api.md`). Тобто частину фільтрації доведеться робити на клієнті, а це конфліктує
з серверною пагінацією: відфільтрувавши 20 товарів сторінки по ціні, можна отримати 3 —
при `total = 194`.

**Варіанти для обговорення.**
1. Фільтр по ціні застосовується тільки до поточної сторінки; чесно підписуємо це в UI.
2. Тягнемо всі товари один раз (`limit=0`), фільтруємо й пагінуємо повністю на клієнті —
   тоді пагінація стає клієнтською і серверну ми не відпрацюємо.
3. Гібрид: пагінація серверна, фільтр по ціні — окремий режим, який вантажить усе.

**Рішення й обґрунтування дописати сюди після Кроку 4.**
